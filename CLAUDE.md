# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`cache_ext` is the SOSP 2025 artifact for customizing the Linux page cache eviction
policy with eBPF. It is a research reproduction harness, not a product. The four
moving parts are:

- `linux/` — a modified Linux v6.6.8 kernel (git submodule) that adds the
  `cache_ext` struct_ops hook into the page cache. Also carries patched libbpf/bpftool.
- `policies/` — eBPF eviction policies (FIFO, MRU, S3-FIFO, LHD, sampling, MGLRU,
  get-scan) plus their userspace loaders.
- `leveldb/`, `rocksdb/`, `My-YCSB/` — benchmark targets (submodules), lightly
  patched to exercise the policies.
- `bench/` + `eval/` — Python benchmark drivers and per-experiment `run.sh` scripts.

Almost everything must run on the custom kernel. Scripts guard this with
`uname -r | grep cache-ext`; if you are not booted into that kernel, builds and
runs will refuse to start. The intended host is a CloudLab `c6525-25g` node with
the repo checked out under `/mydata`.

## Setup / build order

One-time setup, in this order (see README.md for full detail):

```sh
git submodule update --init --recursive
./install_kernel.sh        # builds + installs the custom kernel, libbpf, bpftool
# reboot into "Linux 6.6.8-cache-ext+", then:
./download_dbs.sh          # ~75GB compressed datasets from a public GCS bucket
./install_filesearch.sh ./install_leveldb.sh ./install_misc.sh \
  ./install_ycsb.sh ./setup_isolation.sh ./build_policies.sh
```

Total footprint is ~500GB of disk. The kernel build and dataset download each
take a long time; use `screen`.

### Building just the policies

```sh
./build_policies.sh        # wrapper; refuses to run off the cache_ext kernel
make -C policies -j        # equivalent direct invocation
make -C policies clean
```

`policies/Makefile` uses `clang-14` (pinned — newer clang breaks the kptr_ref
BPF feature) and the patched `bpftool` at `/usr/local/sbin/bpftool`. The first
build dumps `vmlinux.h` from `/sys/kernel/btf/vmlinux`, so it must run on the
running cache_ext kernel.

## Running experiments

Each `eval/<name>/run.sh` sets up cgroups, toggles MGLRU, runs the Python driver,
and writes JSON into the top-level `results/` directory. Map of experiments to
paper figures is in each `eval/<name>/README.md`.

```sh
cd eval/ycsb && ./run.sh          # ~20h by default; uses screen
```

Each `run.sh` has an `ITERATIONS=3` variable (averaged runs) and, where relevant,
a `POLICIES=(...)` array — edit these to shorten a run or test one policy. The
YCSB script also `git checkout`s and rebuilds the correct My-YCSB version, so
expect it to touch the submodule.

Plot results with `bench/bench_plot.ipynb` (writes PDFs into `figures/`).

`results/`, `figures/`, and `__pycache__/` are gitignored.

## Policy architecture

A policy is two files that share a base name:

- `cache_ext_<name>.bpf.c` — the kernel-side eBPF program. It implements a
  `struct cache_ext_ops` (defined in `linux/include/linux/mm_types.h`) and
  exports it via `SEC(".struct_ops.link")`. The ops vtable:
  - `init(memcg)` — usually allocates the policy's data structure(s) via
    `bpf_cache_ext_ds_registry_new_list(memcg)`.
  - `folio_added` / `folio_accessed` / `folio_evicted` — lifecycle callbacks the
    kernel fires as pages enter/are touched/leave the cache.
  - `evict_folios(eviction_ctx, memcg)` — called under memory pressure; the
    policy chooses victims, typically by iterating its list.
  - `admit_folio(admission_ctx)` — optional admission control.
- `cache_ext_<name>.c` — the userspace loader. It opens the BPF skeleton
  (`cache_ext_<name>.skel.h`, generated by bpftool), seeds the watch-dir map,
  loads, then `bpf_map__attach_cache_ext_ops(skel->maps.<name>_ops, cgroup_fd)`
  to attach the policy to a specific cgroup. It stays resident until killed
  (SIGINT) and detaches on exit.

Shared helpers:

- `cache_ext_lib.bpf.h` — the BPF-side API surface. Declares the kernel kfuncs
  (`bpf_cache_ext_list_add/_del/_move/_iterate/_iterate_extended/_sample`,
  `bpf_cache_ext_ds_registry_new_list`), `BPF_STRUCT_OPS[_SLEEPABLE]` macros,
  and reimplemented `folio_test_*` / `READ_ONCE` / random helpers because BPF
  cannot call the kernel's inline page helpers directly.
- `dir_watcher.bpf.h` / `dir_watcher.h` — "watch dir" mechanism. Policies only
  manage folios whose inode is in a watched directory; `is_folio_relevant()`
  checks the inode watchlist before adding a folio. The userspace side walks the
  `--watch_dir` and populates the inode map.

Iteration callbacks return `CACHE_EXT_EVICT_NODE` / `CACHE_EXT_CONTINUE_ITER`
(see `dir_watcher.bpf.h` / kernel headers) to tell the iterator whether to evict
or skip a folio.

Kernel-side implementation lives in `linux/mm/cache_ext.c`, `linux/mm/cache_ext_ds.c`
(the list/data-structure registry and kfuncs), with hooks wired into
`filemap.c`, `vmscan.c`, `swap.c`, and `memcontrol.c`.

When adding a new policy, also add its `.out` target to the `all:` list in
`policies/Makefile` (the `BPF_SRC` variable at the top is stale and not the
source of truth for what gets built).

## Benchmark driver architecture

`bench/bench_lib.py` is the shared core. `CacheExtPolicy` launches a policy
loader as a `sudo` subprocess against a cgroup (default cgroups
`cache_ext_test` / `baseline_test`), waits for it to attach, and kills it with
SIGINT on teardown. The per-workload drivers (`bench_leveldb.py`, `bench_fio.py`,
`bench_filesearch.py`, `bench_twitter_trace.py`, `bench_per_cgroup.py`) build on
it and take `--policy-loader`, `--cpu`, `--results-file`, `--iterations`, and
`--default-only` (run stock kernel / MGLRU instead of a cache_ext policy).

MGLRU must be explicitly toggled around runs via `utils/enable-mglru.sh` /
`utils/disable-mglru.sh`; the `run.sh` scripts do this and it is easy to leave
the system in the wrong state if a run is interrupted.
